## System architecture

- Generated by `requirement:readme` from current requirements and repository code; regenerate this block rather than editing it manually.
- Local-first desktop API client for API developers/testers; no application login, telemetry or new remote-sync service.

| Component | Entry paths | Owns |
|---|---|---|
| Svelte SPA | `src/routes/+page.svelte`, `src/lib/workspace.svelte.js` | UI, active workspace and operation ownership |
| Frontend services | `src/lib/model.js`, `src/lib/transport.js`, `src/lib/persistence-queue.js` | Validation, request preparation and serialized saves/transitions |
| Native backend | `src-tauri/src/main.rs`, `src-tauri/src/lib.rs` | Tauri commands, protocols/auth, files, cancellation/drain and Git |
| Persistence | `src/lib/persistence.js`, `src-tauri/src/storage.rs` | Desktop JSON workspace/previous backup and transition recovery; separate preview localStorage |
| Plugin execution | `src/lib/plugin-runtime.js`, `src/lib/plugin-bun-session.js`, `tools/plugin-runtime/host.js` | QuickJS isolated workers; explicit Bun candidate sessions with owner/capability guards |
| OpenAPI lint | `src-tauri/src/spectral.rs` | Owned Spectral sidecar jobs; bundled executable declared in Tauri config |

- Data: app-data JSON files and assets, not a relational database; preview data never substitutes for desktop persistence.
- External systems: user-configured HTTP/GraphQL/WebSocket/SSE/gRPC APIs, OAuth providers, proxies and Git remotes; tests use local fixtures or approved nonprod.
- Deployment: desktop executables/installers via `scripts/build-desktop.mjs` and `src-tauri/tauri.conf.json`; static SPA configuration is in `svelte.config.js`.
- CI: `.github/workflows/desktop-build-core.yml` defines Linux, Windows and macOS builds; configured targets do not establish runtime acceptance.
- Tooling: Bun only for JavaScript, Cargo for Rust; application frontend stays plain JavaScript.
- Preserve serialized saves, additive imports, trust-boundary validation, writer drain and journal recovery; importing scripts must not execute them.
- Reject stale callbacks/results after owner loss; detached cleanup has no restored store/helper authority.
- QuickJS remains the default until Bun activation, compatibility, platform, resource and packaging/legal gates pass.
- Preserve Insomnium UI during migration; deferred redesign follows completion; code generation supports only Linux/Windows cURL.
- Use saved Playwright scenarios only: shared headless browser launcher; native hosts hidden before CDP and reported as native-hidden; no browser-use tools.
- Requirements: `docs/0-index.md`; completion evidence and retained gates: `docs/migration/STATUS.md`, `docs/migration/PLAN.md`, `docs/migration/PARITY.md`.

## Owner constraint: local Bun is 1.4.4 and must not be downgraded

- Do not run `bun upgrade --version 1.4.2` or otherwise downgrade the installed Bun; owner rejected it (context: [Node.js Brotli RCE, CVE-2026-111497](https://www.sysdig.com/blog/node2shell-cve-2026-111497-detecting-the-node-js-brotli-rce)).
- `package.json` still pins `packageManager: bun@1.4.2`, so `scripts/build-plugin-runtime.mjs` fails with `Use the pinned Bun version`, and `src-tauri/build.rs` fails with `Stale Bun runtime input: package.json` after any package.json change. Resolving this means moving the pin to 1.4.4 (package.json, CI workflows, README/docs, `scripts/generate-spectral-notices.mjs`, Spectral sidecar rebuild); do that as its own topic, not by downgrading.

## Owner rule: finish a topic before documenting it

- Owner correction: conserve the user's usage budget. One work item must deliver a complete user workflow with explicit acceptance criteria. A passing isolated case is evidence, not a new deliverable.
- Keep the chosen defect/workflow active until implementation and its required verification finish. Do not switch to easy passing scenarios while the known defect remains unresolved; switch only for a concrete external blocker or owner steering.
- Read instructions once per unchanged scope. Read only relevant source/evidence afterward; do not reload whole plans, histories or instruction files on every continuation.
- Every investigation step must resolve an implementation decision. If repeated investigation produces no new decision or evidence, change the approach instead of adding more probes or summaries.
- Before a test/build, name the changed behavior or unresolved acceptance criterion it proves. Reuse valid evidence; batch affected verification after a coherent implementation. Do not rerun merely to refresh receipts or edit receipt wording.
- Report the delivered behavior, remaining work and next concrete action briefly. Do not present closed-category ratios as overall completion, repeat old blocker paragraphs in unrelated updates, or create a new progress ledger.
- A user pause remains in force. Workflow/document corrections during a pause do not authorize resuming migration, builds or tests.
